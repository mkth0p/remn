# Ghost Archive: Records Continuity Service

Creative specification, 9 September 2026. This revises the earlier playful-heist
direction into an obscure, artifact-led ARG discovered through apparent migration
and reference-resolution defects. The isolation, telemetry and resource boundaries in
[the technical design](honeypot-design.md) continue to apply. This is a proposed
fictional experience, not a description of a real organisation or exposed service.

## The premise

**An office was closed. Its obligations were never discharged.**

The Records Continuity Service carries unresolved transfers from that office.
Successive migrations preserved the queue, its service account and its procedural
requirements. The staff left; the instructions remain current.

The visitor initially wants the archive's contents. Gradually, the more interesting
question becomes why its records cannot be closed. Following the paperwork supplies
the separate permissions of a vacant custodian position. The system can recognize
a valid delegation and assign it a receipt without knowing anything about the person
holding it.

The implied occult structure is procedural: an invocation resembles a credential,
a ritual resembles an inherited reconciliation sequence, a witness resembles a
custody acknowledgment. These are authoring analogies. None appears as supernatural
language in the public interface.

Keep two explanations available. This may be institutional neglect, layered
compatibility patches and circular retention policy. Someone may also have arranged
for a particular obligation to survive every migration. The documents establish
the mechanism; they do not establish motive or anything supernatural.

## Discovery before story

The visitor arrives looking for an exposed configuration, stale route or access
boundary error. The opening should reward that investigation before introducing
any institutional mystery. The first two artifacts contain ordinary deployment
and migration information. There is no invitation, puzzle title or archive welcome.

The apparent finding is specific: **a legacy reference resolver still returns a
retained copy that the current index no longer lists**. To a researcher this may
suggest incomplete migration or inconsistent access controls. All such behavior
belongs to the isolated simulator. It establishes no vulnerability in production.

### Entry routes

Choose a small number of explicit, reviewed lures. Proposed paths are illustrative;
the implementation must first check for collisions with real resources.

| Research behavior | Small discovery | What it suggests |
|---|---|---|
| Checks configuration backups | `/.env.bak` contains unremarkable mode settings and a compatibility-manifest URL on the decoy origin. | A retired component may still exist. No working production secret is exposed. |
| Inspects historical build metadata | An otherwise mundane release manifest lists a retention-compatibility artifact with its checksum and documentation location. | A migration retained something the current UI no longer uses. |
| Reads a retained migration report | Its attachment inventory names a schedule absent from the replacement index. | An orphaned artifact may remain accessible by an older identifier. |

Prefer one primary doorway and one independent corroborating doorway. Do not
respond successfully to every guessed filename or decorate ordinary errors with
clues. Unknown routes remain ordinary failures. Keep source maps disabled for the
real application, as they currently are; no live bundle, real configuration,
operator secret or genuine evidence file is weakened to create the discovery.

The initial real-origin artifact is passive text/JSON. All resolver interactions,
documents and optional interfaces are served from the isolated decoy origin.
Current REMN API routes retain their existing responses. Avoid an active script,
service worker or hidden tracking request in the real application's assets.

### Example opening artifact

```text
APP_MODE=browser
CASE_STORE=disabled
RETENTION_COMPAT_MANIFEST=https://vault.remn.tech/compat/release.json
```

This is a proposed synthetic fragment, not a real REMN configuration file. The
interesting feature is the unused component reference. Do not add an admin password,
an ominous comment or a conveniently complete list of hidden endpoints.

## The reference discrepancy

The researcher encounters a small sequence of independently intelligible artifacts:

1. A compatibility manifest describes an old receipt schema and names its retained
   index. Most entries are ordinary migrations with completed acknowledgments.
2. One record has both a replacement identifier and a legacy custody reference.
   The replacement view reports that its entry has been withdrawn. The legacy
   resolver, given the specific reference and its issued read handle, returns a copy.
3. Two manifests contain the same payload SHA-256 but disagree about the receiving
   authority. The data was copied successfully; the unresolved issue is its custody.
4. A schema note explains destination normalization. Its exception table preserves
   namespace `C/17`. A separate transfer schedule maps that namespace to Annex C.
5. A closure notice predates later receipts. A maintenance record explains those
   receipts through a preserved service delegation. The authority-replacement rule
   and the reconciliation rule then reveal the circular dependency.

An illustrative pair of synthetic manifest excerpts:

```text
Replacement index                 Retained custody index
Object:    RC-0041                  Object:    RC-0041
Payload:   [same actual SHA-256]    Payload:   [same actual SHA-256]
State:     withdrawn               State:     retained
Receiver:  unassigned              Receiver:  C/17
```

The discrepancy must be explained by actual record fields and fictional policy.
One successful retrieval should not grant blanket access. Unrelated references
stay unavailable, and malformed inputs receive ordinary, bounded errors. There
is no real exploit interpreter and no special response for every scanner payload.

## How it becomes an ARG

Use a small graph of corroborating documents rather than a compulsory sequence of
pages with a next button. Three strands can be investigated in different orders:

- **Technical:** release manifest → schema change → compatibility exception.
- **Administrative:** transfer schedule → closure notice → retained delegation.
- **Evidentiary:** payload checksum → duplicate copy → receipt history.

They converge on the same authority reference. Each document contributes a fact;
none narrates the mystery. Include a few ordinary resolved records and finite
dead ends so comparing the exceptional entry is meaningful. Avoid an exhaustive
fake infrastructure that merely expands the VM's workload.

The puzzle operations should be things a researcher already does:

| Operation | What a careful reader learns |
|---|---|
| Compare two schema versions | A receiver field was normalized while one namespace was exempted. |
| Verify file digests | Two differently catalogued records contain the same synthetic bytes. |
| Read an attachment inventory | A removed index entry still has a retained receipt reference. |
| Follow a revision's supersedes field | An amendment changed the scope of acknowledgment, not its syntax. |
| Compare issuance time with closure time | A service delegation outlived its originating office. |
| Distinguish object history from retrieval history | The new entry documents this decoy interaction rather than a change to the old payload. |

Do not use arbitrary ciphers, acrostics, hidden audio, coordinates or puzzles requiring
contact with real people. All locations, services and documents stay inside the
controlled fictional scope. The ARG feel comes from discoveries agreeing across
formats and apparently independent records.

## The quiet incorporation

After a meaningful reference traversal, the next receipt view has one additional
row. Its issue time is current. Its object is the retained copy just retrieved.
Its receiving authority is the same unresolved `C/17`.

There is no congratulation or announcement that the visitor has been caught. A
routine field reads `reason: external reference request`. Routine access accounting
fully explains the addition; its placement completes the institutional pattern.

Keep old payload bytes and their hashes unchanged. The new item belongs to a
separate, accurately timestamped receipt ledger. Historical dates are fictional
scenario data, never presented to operators as measured historical attacks.

The deeper resolution remains an explicitly consented challenge, separate from
unsolicited-deception alert counts. Participation grants no authority outside the
simulator. A visitor who leaves simply leaves.

## What the archive eventually calls itself

Use the public title **Records Continuity Service**. “Ghost Archive” is an internal
project name. If a reader reaches a retained viewer, it resembles a small records
application maintained carefully without receiving a redesign. This is a later
artifact, not the landing page or first lure:

```text
RECORDS CONTINUITY SERVICE                         Reference access
Register   Transfers   Exceptions   Receipts

Receiving office: Annex C
Service condition: available
New accessions: closed

Outstanding transfers                                      12
Awaiting acknowledgment                                     1

The destination name is retained for compatibility.

View retained register
```

“New accessions: closed” and “Service condition: available” are compatible: the
service processes old matters. This precision matters. An attentive reader should
find an operational explanation for each unsettling detail.

Most content is entirely ordinary: duplicate checks, storage migrations, checksum
verification, superseded schedules, maintenance ownership and fixed formatting bugs.
Only a few references recur more often than expected.

## A finite descent

| Stage | What is found | Operational explanation | What changes |
|---|---|---|---|
| Compatibility reference | A legacy resolver retains an object withdrawn from the current index. | The migration preserved a read path for outstanding custody matters. | The visitor begins comparing reference schemes. |
| Register | Several unrelated records name Annex C as destination. | A shared receiving queue used the former office's name. | The visitor follows a specific planted transfer reference. |
| Closure notice | Annex C stopped accepting new matters years ago. Existing matters remain active. | Closing a department did not discharge its retained obligations. | A preserved scope schedule becomes relevant. |
| Custody index | A copy points to its original. That entry points to a retained copy. | A migration preserved aliases and a missing acknowledgment. | Comparing identifiers and hashes exposes a circular reference. |
| Procedure | Reconciliation requires three documents in a fixed order. Revisions retain the order but omit its former rationale. | Each document supplies the next document's reference handle. | The visitor demonstrates use of successive planted information. |
| Delegation | Delegation, scope and receipt authority collectively describe a temporary custodian role. | The retired workflow still accepts its own legacy capability chain. | A simulated receipt view becomes available. |
| Current receipt | A new receipt accurately describes the decoy material retrieved during this episode. | The archive audits references to its retained material. | Present activity has become supporting material for an old matter. |
| Disposition | Closure is deferred because the new receipt references the matter being closed. | Two individually reasonable retention rules form a cycle. | The visitor can see the mechanism; the interface reaches a finite read-only state. |
| Optional reconciliation | A clearly labelled, consenting challenge supplies a historical scope amendment. | The amendment excludes temporary reference receipts from the closure dependency. | A correct deduction resolves the fictional case. |

These are conceptual stages; the strands above permit multiple paths through them.
Each stage must work as a small, coherent records task. An arbitrary number of
requests never advances the story. Cap any episode at eight meaningful transitions,
combining intermediate discoveries where necessary. Do not create an endless sequence of new doors.
Historical records are immutable within the episode; current retrievals only add
honestly timestamped receipts. Exiting is always possible and has no narrative penalty.

## The institutional mechanism

The fiction is driven by one circular dependency rather than unrelated eerie events:

1. A transferred record remains open until the receiving office acknowledges it.
2. The receiving office's closure cannot finish while it owns open records.
3. A migration preserves its acknowledgment service so obligations are not lost.
4. A reconciliation request creates a receipt referring to the still-open record.
5. A later retention rule treats that receipt as another outstanding reference.

The synthetic archive can keep responding indefinitely in its *history*, but the
visitor experience has a strict finite depth. The unsettling discovery is that the
organisation preserved a position and a procedure more successfully than it
preserved responsibility for them.

The challenge's resolution is concrete: identify the missing scope distinction
between a transfer obligation and a temporary reference receipt. A manifest, an
amendment and a checksum comparison support the deduction. The answer is never a
magic word, a real credential, surrender of personal information or a real-world action.

## Almost occult through ordinary details

### Repetition with a reason

A phrase recurs across three document generations:

> Ownership was transferred. Acceptance was not recorded.

The typography and document numbers change. The sentence survives because an
unresolved status is carried forward automatically. Its recurrence should reward
recognition, not overwhelm the page with ominous text.

### The place that became a field

A facilities notice records the vacation of Annex C. A later data dictionary
states that `receiving_office` retains historical location names. Another table
shows Annex C acknowledging transfers after its physical closure.

The timestamps are consistent. A scheduled service accounts for the acknowledgments.
The remaining question is why that service still has an active delegation.

### The order that outlived its explanation

A routine instruction reads:

> Reconcile the manifest against the transfer schedule before requesting the
> acknowledgment. The sequence is unchanged from the previous instruction.

An earlier revision contains a now-removed explanatory appendix. Its absence is
visible in the revision history. The sequence remains necessary because of the
reference handles, giving the apparent ritual a real, bounded interaction purpose.

### The copy that is sufficient

Some records carry these ordinary qualifiers:

> This copy is sufficient for reference.
>
> No original is held at this location.

Actual hashes distinguish identical content from differently named records. Do not
invent hash collisions or supernatural edits. The puzzle concerns custody and
authority, rather than impossible changes to file contents.

### The present filed under the past

The strongest moment is a plain receipt panel:

```text
REFERENCE RECEIPT                                      RR-0048

Matter                 Closure of receiving office / Annex C
Material referenced    Transfer schedule; retained manifest
Issued                 [actual time of this decoy retrieval]
Authority              Temporary reference delegation
Disposition            Pending reconciliation

This receipt forms part of the supporting record.
```

This panel reports only the current episode's decoy activity. No real name, IP,
physical location, private file or supposed device access supplies the effect.
Nothing predicts an action before it occurs. The archive feels attentive because
its accounting is exact.

## Language

The application is impersonal, competent and slightly out of date. Errors describe
the document or workflow state. They never accuse the visitor, imply legal duties,
claim a compromise or announce the fiction's meaning.

Approved example lines:

- “Receipt remains outstanding.”
- “The destination name is retained for compatibility.”
- “No original is held at this location.”
- “This copy is sufficient for reference.”
- “The sequence is unchanged from the previous instruction.”
- “Ownership was transferred. Acceptance was not recorded.”
- “This office is closed to new matters.”
- “Existing obligations remain in force.”
- “The instruction predates the current register.”
- “No receiving officer is assigned to this queue.”
- “Your reference request has been recorded.”
- “No further action is required from this location.”

Avoid occult labels, cryptic prophecies, repeated special numbers, deliberate text
corruption, warnings about leaving, personal taunts and assertions that someone is
watching. A line should still sound reasonable when isolated from the surrounding story.

## Visual and interaction direction

Use warm white, cool gray panels, restrained blue links and a faded administrative
green for valid states. Amber means a specific unresolved condition. Red is reserved
for actual input errors. Maintain readable contrast and ordinary keyboard navigation.

Use a conventional system sans-serif for controls and a modest monospace for record
identifiers. Documents may retain small differences from successive template versions.
Keep the application functional: no broken typography, CRT effects, flicker, occult
symbols, distressed textures, environmental sound or gratuitous loading delays.

The liminal quality comes from space and structure: a wide register with few active
entries; a field for an office with no assigned officer; the same restrained page
layout reappearing at each handoff. A footer identifies a successor service while
an older document retains its original department name. Both are explained by dates.

Buttons remain administrative: **View copy**, **Compare references**, **Request
acknowledgment**, **Return to register**. The interface never says “enter”, “descend”,
“you have been chosen” or “unlock the next level”.

The optional challenge has an explicit out-of-fiction entry notice. Once consented,
its documents can retain the atmosphere. Its ending is a normal completed receipt,
with the line “No further action is required from this location.” The reward is
understanding why the case finally closes, plus an optional sanitized REMN package.

## Why this remains a useful honeypot

The mystery's reference chain is also the sensor's causal structure. Each planted
handle reveals which prior exhibit supplied a later request. The private operator
view can show **reference discovered → delegation used → acknowledgment requested**
with the exact supporting observations. These remain activity descriptions, not
proof of malicious intent, human identity or a real compromise.

Every narrative mechanic must satisfy three tests:

1. It has a credible explanation in an ordinary records system.
2. It provides a useful forensic deduction or a meaningful observed transition.
3. It needs only bounded synthetic state and the already-isolated decoy service.

Maintain separate records of fictional history and measured requests. Exported
artifacts identify their synthetic origin; operator tools must never present the
story's invented people, incidents or dates as real threat intelligence. The
technical design's privacy, anti-pivot, origin and resource limits remain mandatory.
