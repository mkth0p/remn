# REMN 2.0: the investigation that proves itself

24 September 2026. Branch `browser-only-mode`, HEAD `b7a87d8`. This plan continues the
[browser-only analysis of 22 September](2026-09-22-browser-only-analysis.md): it keeps that
analysis's pillar numbering where an item carries over (1b, 2a, 3e…), and says what has been
built since.

## 1. North star

**Open a web page, drop the evidence, and get an answer you can prove, without the evidence
ever leaving your machine.**

REMN 2.0 is an investigation workbench that runs entirely in the analyst's browser, from a
build anyone can check. It reads Windows, Microsoft 365 and mail evidence, tells the story of
each person and machine involved, names what it could not see, and issues a report where each
sentence points to the bytes it rests on, together with the file a second examiner needs to
check it. A local model works the case beside the analyst; it is measured, its claims are
checked, and it changes nothing without a click.

## 2. What is new

Four shifts, each against REMN 1.x and against the field.

**1. No upload, no install, no server that sees the evidence.** Today every file goes to the
REMN server (remn.tech, or the analyst's own) to be parsed, even in browser-only mode.
Timesketch and Velociraptor need a server; Hayabusa and Chainsaw are command-line tools with
no case; AXIOM and Cyber Triage are desktop installs with licences. In 2.0 the analyst opens
remn.tech on a borrowed laptop, drops a KAPE collection, and the network tab shows no request
that carries evidence. The page they ran is the commit on GitHub, and they can check that.

**2. Conclusions you can re-derive.** A 1.x report is a well-made document; a reader has to
trust it. A 2.0 report carries a manifest: the hash of each evidence file, the rule set, the
REMN build, and the head of the decision journal. The other side's expert drops the report
and the original files on the verify page (or runs a small independent script) and gets,
claim by claim, "found in the evidence" or "not found". Nobody in DFIR ships that today.

**3. The story of a person, with its gaps named.** 1.x builds chains that start from a mail.
2.0 builds a story from any seed (a person, a machine, a finding): one identity across mail,
Entra, the Unified Audit Log and Windows, their sessions and process trees, in time order,
and a list of what the evidence cannot show ("no Sysmon on WS07: process lineage limited to
4688", "Security log records 18200 to 18450 missing").

**4. A co-investigator that is measured and checked, on the analyst's own hardware.** AI 2.0
already plans, cites and proposes. In 2.0 it triages each new piece of evidence on its own,
its factual claims are checked against the rows they cite (not only that the rows exist),
and every local model is scored on an open benchmark built from REMN's lab, whose ground
truth is known. The analyst picks a model by its measured results, not by its name.

A fifth shift, **handing a case over without a server**, follows in 2.1.

## 4. Principles

Every decision in 2.0 is checked against these.

1. **Evidence stays where the analyst puts it.** In the browser by default, on the analyst's
   own server if they choose. Anything that leaves is named, per file, before it leaves.
2. **The analyst decides.** Models, rules and correlation propose; a person accepts, with a
   name and a time in the journal.
3. **Every statement points to a record, and every gap is named.** A claim without a record
   is a hypothesis and reads as one.
4. **Measured, not claimed.** A rule, a parser or a model shows how it was measured, on what.
5. **One implementation per piece of logic.** A second implementation exists only to check
   the first, and only for a set time.
6. **Each milestone ships alone and is useful alone.** Nothing waits for a big-bang release.

## 5. The pillars

Effort, for one maintainer working with AI assistants: S up to a week, M 2 to 4 weeks, L 1 to
2 months.

### A. The tab is the lab

**What:** EVTX, Microsoft 365 exports and investigation packages are parsed in the
browser's ingest worker. Server parsing stays only for formats the browser cannot read yet
(PST/OST, MSG, registry hives through dissect), and each such upload is labelled.

**Stories:**
- A consultant opens remn.tech for a client's case; the EVTX never leaves the laptop.
- An in-house responder with no approved server runs the whole case offline.

**Exists today:**
- `frontend/src/workers/ingest.worker.ts` (streams server rows into IndexedDB);
- the Python parsers:
  - `backend/services/parsers/evtx_parser.py` (645 lines);
  - `m365.py` (867);
  - `collection.py` (959);
  - `backend/services/ingest/package.py` (695);
- the golden corpus and `tools/evtx_attack_samples.py`, which freeze the rows those parsers
  produce;
- the CSP already allows `'wasm-unsafe-eval'`.

**New:**
- **EVTX (6c, L).** The Rust `evtx` crate, the one REMN already uses through pyevtx-rs, compiled
  to WebAssembly and called from the ingest worker. Flattening (field map, access names,
  lineage fill, summaries) is ported to TypeScript in `frontend/src/parse/evtx/`, with row
  parity against the golden corpus and the attack samples.
- **M365 (6d, M).** Unified Audit Log CSV/JSON and Graph sign-ins in TypeScript
  (`frontend/src/parse/m365/`), same parity rule.
- **Packages (M).** ZIP read as a stream in the worker, with a per-member manifest. EVTX and
  M365 members parse locally; hives and other artefacts go to the server tier only when
  the analyst allows it, otherwise they are listed as "not read, reason".
- **Capability tiers (1a, S).** Each evidence item shows "parsed in this browser" or
  "parsed on <host>, nothing kept". The report prints the same line per file.
- **Verifiable build (6b, M).**
  - Reproducible frontend build (pinned toolchain, fixed timestamps), with a digest per
    commit published by CI.
  - remn.tech serves `/.well-known/remn-build.json`, and `tools/verify_instance.py` compares
    it with a local build.

### B. Proof-carrying investigation

**What:** stable identities for every row, one journal for every decision, exhibits a
second examiner can find in the originals, a completeness ledger, and a report that can be
checked against the evidence.

**Stories:**
- Opposing counsel's expert receives the report and the manifest. They drop both, with the
  client's original files, on the verify page, and see 41 of 41 claims found in the evidence.
- A second expert checks the same 20 exhibits with EvtxECmd, without REMN.

**Exists today:**
- `recordKey` on cloud rows;
- `RowProvenance` on row marks (`frontend/src/data/rowMarks.ts`);
- the AI ledger (`frontend/src/ai/ledger.ts`, table `aiLedger`) and its hash chain;
- the report preflight (`frontend/src/data/reportPreflight.ts`);
- the package member manifest;
- case bundles that carry their rules (`frontend/src/data/caseBundle.ts`).

**New:**
- **Content-derived identity (2a, M).** Every row gets a `recordKey` built from its file's
  SHA-256 and a locator:
  - EVTX: channel, EventRecordID and chunk offset;
  - mail: member path and Message-ID;
  - UAL: record id.
  Findings, decisions, marks and citations point to record keys, not row numbers, so a
  re-ingest or a bundle import no longer renumbers conclusions.
- **One journal (2b, M).** The AI ledger becomes the case journal. Every decision, by the
  analyst or accepted from the AI, goes through one `decide()`, with actor, before, after and
  a hash chain. The Review page, row marks, notes and report issue all write through it.
- **Completeness ledger and time (1b, 1c rest, M).** Per file:
  - records read, skipped and failed;
  - EventRecordID ranges and their holes;
  - every limit that cut data.
  The report's "Where it stops" is generated from it.
- **What the evidence cannot tell (1e, M).**
  - A source-by-tactic coverage statement (no Sysmon, no PowerShell logging, audit policy
    gaps, cleared logs).
  - A statement per question in the answer sheet.
- **Exhibits (2d, M).** Each cited row exports as an exhibit: file hash, locator, the
  original XML or raw record, and a manifest.
- **The report manifest and the verify page (M).**
  - The report embeds a manifest: evidence hashes, rule set digest, build id, journal head,
    and the claims with their record keys.
  - The verify page re-parses the dropped evidence, re-derives each cited record, compares
    content hashes and claims, and prints pass or fail per claim.
  - A small independent script (`tools/remn_verify.py`, python-evtx rather than REMN's
    parser) checks the exhibits, so verification does not depend on trusting REMN.
- **The answer sheet (2f, M).** For each key question, the answer, with citations or
  "Not determinable" and why:
  - initial access;
  - accounts;
  - hosts;
  - what ran;
  - what was accessed;
  - persistence;
  - is it still active.

### C. One person, one story

**What:** an identity resolver, host lineage, and a story engine that starts from any seed
and lists its gaps.

**Stories:**
- The analyst clicks alice.martin and sees, in one timeline:
  - her phish;
  - the inbox rule;
  - the sign-in from 203.0.113.66;
  - the RDP session to WS07;
  - the process tree it spawned;
  - "no mailbox access log after 10:40: MailItemsAccessed not exported".

**Exists today:**
- chains (`frontend/src/data/chains.ts`, mail-seeded);
- relationship stories (`frontend/src/workers/stories.worker.ts`,
  `frontend/src/data/relationshipStories.ts`);
- the account normalisation used by chains;
- the on-demand `process_tree` and `logon_session` in `frontend/src/ai/tools.ts`.

**New:**
- **Identity resolver (3b, L).** In a worker. It joins:
  - UPN, SAM and domain;
  - SID;
  - mail address;
  - display name;
  - Entra object id.
  Each merge has a confidence, and a bare-name match reads "possibly the same".
- **Host lineage (3e, L).** Process trees and logon sessions (4624 to 4634, RDP hops)
  materialised per host in a worker, once per ingest.
- **Story engine (L).** Chains generalised: seed on a person, a host or a finding. It
  assembles mail, sign-ins, audit records and host activity, attaches findings, and ends
  with its gaps. Stories feed "What happened" in the report.
- **Six areas instead of sixteen views (M).**
  - Intake, Triage, Stories, Hunt, Decide, Report.
  - The views keep their code; the navigation and the Dashboard change.

### D. A checked co-investigator

**What:** the agent works on new evidence by itself, its claims are checked, and it drafts
report sections bound to claims.

**Stories:**
- The analyst drops a collection and goes for coffee. On return, the inbox holds:
  - eleven proposals;
  - three hypotheses;
  - a draft "what happened".
  Each sentence carries a green or red claim check.

**Exists today:** AI 2.0 (`frontend/src/ai/`):
- the agent loop;
- playbooks;
- the inbox;
- the ledger;
- the evidence boundary;
- the context engine.

**New:**
- **Triage on ingest (M).** When a file finishes, the agent runs the playbooks that fit,
  within a budget, in the background. Proposals only.
- **Claim checking (M).** Answers and drafts emit structured claims (who, what, where,
  when, cites). Each claim is checked by a deterministic query on the cited rows, for
  example: user equals alice, IP equals 203.0.113.66, time within one minute. The result
  shows as supported, contradicted or unchecked. This moves from "the row exists" to "the
  row says so".
- **Drafted sections (M).** "What happened" and the answer sheet drafted from the story,
  sentence by sentence, each bound to its claims, through the inbox.
- **Model check (S).** Ten minutes of the benchmark (pillar E) on the analyst's own model,
  with a scorecard and a recommendation for their hardware.

### E. Measured, not claimed

**What:** every default rule, parser and model carries a measurement the analyst can see.

**Exists today:**
- the attack-samples CI job and `tests/fixtures/evtx-attack-samples/expected.json`;
- the rule-check bench used for the 75 new rules (it lived in a scratch directory; it moves
  into `tools/`);
- the lab and its ground truth;
- the golden corpus;
- engine parity fixtures.

**New:**
- **Detection harness (4a, 4b, 4c, M).** Per rule, in the Rules view and on each finding:
  - fired on N of M samples of its technique;
  - X benign hits per 10,000 background events;
  - last measured on commit C.
  Hayabusa and REMN findings on the same records are fused. Rules with no measured sample
  become hunt signals, not findings.
- **REMN-Bench (M).** The lab's nine stories, their answer sheets and the injection suite,
  run against any local model through the Ollama or OpenAI-compatible API. It scores:
  - story recall;
  - citation precision;
  - claim accuracy;
  - proposals correct;
  - injection resistance;
  - time per task.
  Results are published in `docs/`, per model and quantisation. It would be the first open
  benchmark of local models on forensic agent work with known ground truth.

### F. Handing over without a server (2.1)

**What:** a case passes from one analyst to another through any channel, and a second
examiner reviews it.

**New:**
- **Encrypted bundles (M).** WebCrypto X25519 plus AES-GCM, or a passphrase.
- **Second-examiner mode (M).** Each decision is shown for confirmation or dispute; disputes
  go to the journal.
- **Journal merge (M).** Between two copies of a case. The journal is append-only with actor
  ids, so the merge is a union.
- **Mail in the tab (L).** EML and mbox in TypeScript, with the mail analysis and risk score
  ported under parity. PST, OST and MSG stay on the server tier.
- **Offline.** REMN Local and a service worker (6e).
- **Not planned:** live multi-analyst editing.

## 6. Architecture

**What changes:**
- **One parser, two places to store.**
  - Parsing moves into the browser (TypeScript, plus one WebAssembly module for EVTX).
  - For large cases the browser streams parsed rows to the analyst's own REMN server,
    which writes DuckDB, instead of uploading files.
  - Python parsing remains for PST/OST/MSG and dissect triage, and as a labelled fallback.
  - The server's EVTX and M365 parsers are retired one release after the browser path
    reaches parity. Until then the golden corpus holds both to the same rows.
- **Record keys everywhere** (Dexie version 7):
  - existing EVTX and cloud rows are back-filled from `sourceSha256`, `recordId`, `channel`
    and `recordKey`;
  - rows that cannot be back-filled mark their case "pre-2.0 identities";
  - bundle format 3 imports format 2.
- **The journal replaces the AI ledger**, as a superset. Existing ledger rows become journal
  rows, with their hashes kept.
- **Workers:**
  - ingest (parse);
  - query;
  - rules;
  - stories;
  - identity and lineage (new);
  - claims (new).
- **Crypto through WebCrypto:**
  - SHA-256 for manifests;
  - Ed25519 signatures optional in 2.1;
  - X25519 plus AES-GCM for bundles.
- **Deployment:**
  - remn.tech serves the static app, the build manifest, and a parser for the server-tier
    formats only.

**What stays:**
- Dexie as the browser store;
- the rule language and both engines with their parity fixtures;
- the approval inbox and its rule that nothing is written without a click;
- the public deployment's hardening;
- the case bundle as the unit of exchange.

**Deliberately not rebuilt:**
- DuckDB-WASM, unless a 10-million-event benchmark in M3 shows Dexie with workers cannot
  hold a real case.
- Pyodide: its first load is 15 to 40 MB, and TypeScript ports under golden parity keep one
  language in the browser.
- A graph canvas before lineage tables exist.

## 8. What 2.0 will not do

- **No new platforms:** no Linux, macOS, AWS, GCP, Okta or Google Workspace parsers. REMN
  reads KAPE, Velociraptor and Zimmerman output correctly instead. After 2.0, the
  browser-parser framework makes CloudTrail and Okta JSON cheap, one source at a time,
  each with golden files.
- **No cloud models, no API keys, no WebGPU.**
- **Not a SIEM:** no streaming ingest, no alerting, no always-on collection.
- **No live multi-analyst editing.**
- **No rule-count marketing:** measured coverage replaces it.
- **No second implementation kept "just in case"** after parity is proven.
- **What REMN stops doing:**
  - adding top-level views;
  - server-only analysis endpoints;
  - exporting every observed value as an indicator;
  - the honeypot in this repository.

## 10. Risks

- **WebAssembly EVTX is too slow or too hungry.** The M1 spike decides; the server tier stays
  the labelled fallback, and 2.0 still ships the proof and story pillars.
- **Two parsers during the transition.** The parity harness holds them together; the server's
  EVTX and M365 paths are retired one release after parity, on a set date.
- **Browser storage.**
  - Quota, and eviction: Safari removes a site's storage after 7 days without use.
  - Answers: `persist()`, a size estimate before ingest, streaming rows to the analyst's
    own server for large cases, and Safari labelled for evaluation.
- **A verify page that trusts REMN.** An independent script (python-evtx) checks the
  exhibits, and the manifest format is documented, so anyone can write a third check.
- **One maintainer, seven months.**
  - Every milestone ships alone.
  - The "will not do" list is enforced.
  - Each exit is measured before the next starts.
- **Local models vary.** The benchmark says which ones hold up; the agent never decides.
- **Licences.** No GPL or AGPL code goes to the browser (TypeScript ports, MIT-licensed
  libraries). dissect and extract-msg stay on the server tier. REMN stays Apache-2.0.
- **Old cases.** The version 7 migration back-fills record keys where it can and labels the
  rest; bundle format 2 still imports.

## 11. Decisions for the owner

**Decided on 24 September 2026:** decisions 1 to 4 as recommended.
- 2.0 goes deep on Windows, Microsoft 365 and mail, with no new platform.
- M1, EVTX in the tab, comes first.
- EVTX is decoded by the Rust `evtx` crate compiled to WebAssembly.
- EML and mbox move into the tab in 2.1; PST, OST and MSG stay on the server tier.
Decisions 5 to 10 are open, and are taken before the milestone that needs them.

1. **Scope.** 2.0 goes deep on Windows, Microsoft 365 and mail, and adds no new platform.
   *Recommended.* The alternative is to add Linux, macOS or cloud sources now, which roughly
   doubles M3.
2. **First milestone.** Start with EVTX in the tab (M1 as written), or with the
   proof-carrying record (M2 first, no Rust needed). *Recommended: EVTX first.* remn.tech
   takes real cases today, and uploads are its biggest trust gap.
3. **How EVTX gets into the browser.** The Rust `evtx` crate compiled to WebAssembly, the
   same decoder the server uses. *Recommended.* The alternative is a TypeScript EVTX
   decoder: no Rust toolchain in CI, but a second decoder to prove.
4. **Mail in the tab.** EML and mbox in 2.1, with PST, OST and MSG on the server tier for
   good. *Recommended.* The alternative is mail in 2.0, which adds about two months.
5. **Server parsing on remn.tech after M3.** Only for PST, OST, MSG and hives, labelled per
   upload. *Recommended.* The alternative is to keep the server path for every format as an
   option.
6. **Signatures.** Hash manifests in 2.0 and analyst signatures (Ed25519) in 2.1.
   *Recommended.*
7. **Navigation.** The six areas in M4. *Recommended.*
8. **Safari.** Labelled for evaluation, because of its 7-day eviction. *Recommended.*
9. **Old cases.** Migrate where record keys can be computed, and label the rest.
   *Recommended.*
10. **Version names.**
    - Each milestone as a 0.x release (0.2 to 0.6), and 2.0 when M5 ships, skipping 1.0
      because 0.1 already covers what a 1.0 would.
    - The alternative is to number the milestones 1.1 to 1.5.
